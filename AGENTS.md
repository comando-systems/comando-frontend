# AGENTS.md

## Project goal

Build the Comando universal frontend: one Expo/React Native application for **web and Android** that talks to the [comando-backend](https://github.com/comando-systems/comando-backend) API. iOS-compatible code is welcome, but iOS is not a release target. Prioritize mobile-first layouts, performance, and cross-platform behavior.

The product covers authentication, the catalog, counter sales, table orders, order building and payment, and an administrator-only management area.

## Language and communication

- All source identifiers, filenames, comments, tests, commit messages, pull request titles/descriptions, issue content, and documentation must be written in **English only**.
- User-facing UI copy is written in **Brazilian Portuguese** (including buttons, labels, placeholders, accessibility labels, validation and error messages). Product terms such as `Mesa N` are Portuguese by design. Backend messages are never leaked raw: present a fixed Portuguese translation instead.
- Keep code identifiers and test IDs in English; only the displayed text and accessibility labels are Portuguese.
- Commit messages and PR titles follow Conventional Commits and use imperative wording.

## Repository, branches, and delivery

- Public repository: `github.com/comando-systems/comando-frontend`. The earlier implementation is archived in the private `comando-systems/comando-frontend-bkp` repository and is not a source for this project.
- Default branch is `main`. An active GitHub ruleset blocks direct pushes, deletion, and force pushes, and allows **squash merge only** with zero required approvals and no bypass actors.
- Never commit directly to `main`. Work on short-lived branches named `feature/<issue-number>-<slug>`, `fix/<issue-number>-<slug>`, or `docs/<slug>`.
- Every change lands through a pull request that closes its issue (`Closes #N`) and is squash-merged.
- Do not create issue-tracking files inside the repository. Issues live only on GitHub.
- Keep secrets out of source control. `.env` and `.env*.local` are ignored; commit `.env.example` only.

## Expo and dependency policy

- Current SDK: Expo 58, React Native 0.88, React 19.3, `react-native-web` 0.21. Read the versioned docs at <https://docs.expo.dev/versions/v58.0.0/> and the index at <https://docs.expo.dev/llms.txt> before touching Expo, EAS, or React Native APIs. Do not rely on remembered APIs.
- `pnpm-lock.yaml` is the lockfile. Use `npx expo install <package>` for Expo-compatible versions (not `pnpm add` or `npm install` for SDK packages) and `pnpm` for scripts. Never commit a second lockfile.
- Runtime building blocks: `expo-router`, `react-native-safe-area-context`, `react-native-screens`, `expo-linking`, `expo-constants`, `expo-status-bar`, `react-native-web`, `react-dom`, `@expo/metro-runtime`, `expo-secure-store`, `expo-font`, and `@expo/vector-icons`.
- Development: `jest-expo` with Jest 30, `@testing-library/react-native` 14+, and `eslint-config-expo` via `npx expo lint`.
- `@expo/vector-icons` is allowed only because the product asked for it. It is deprecated upstream; the internal `Icon` adapter is the only file allowed to import it so a later migration stays local.
- No `android/` or `ios/` directories are committed. Native projects are generated by Continuous Native Generation; configure native behavior in `app.json` and config plugins only.
- Prefer first-party Expo modules. Do not add a native library without checking that it works on web or providing a web adapter.

## Source layout and entry point

All application source lives under `src/`. Configuration files (`app.json`, `package.json`, `tsconfig.json`, `eslint.config.js`) stay at the repository root.

```text
src/
  index.tsx                 Single application entry point
  app/                      Expo Router route files only; thin re-exports
  components/<name>/        One directory per reusable component
    index.tsx               Component implementation
    <name>.test.tsx         Colocated test
  screens/<name>/           One directory per screen
    index.tsx               Screen implementation
    <name>.test.tsx         Colocated test
  services/                 API client, storage, and backend adapters
  types/                    Shared domain and API types
  providers/                React context providers
  hooks/                    Reusable hooks
  utils/                    Pure helpers
```

- `package.json` sets `main` to `src/index.tsx`. That file initializes side effects when needed and imports `expo-router/entry` **last**. There is no root `App.tsx` and no root `index.ts`; they are the same file as `src/index.tsx`.
- Routes in `src/app/` only declare navigation and re-export screens, for example `export { default } from '@/screens/login';`. Business logic never lives in a route file.
- Use `@/*` as the TypeScript alias for `src/*`. Import from a package's `index.ts` instead of reaching into internals.
- Name components after what they are: `Button`, `Card`, `Login`, `Tables`. Never use `ButtonComponent`, `HomeScreen`, or `LoginView` suffixes.
- Every component and screen directory contains at least one meaningful test file beside its implementation. Name test files `<name>.test.tsx`.
- Keep files focused. Do not create a layer or abstraction until two concrete call sites need it.

## Navigation and access control

- Expo Router file routes under `src/app/`. Use `Link`, `Stack`, `Tabs`, `Redirect`, `useRouter`, and `useLocalSearchParams` from `expo-router`. Prefer `useRouter()` in components; prefer complete hrefs for nested navigation.
- Root layout holds providers and protected-route guards. Authenticated routes live in a `(app)` group; `login` stays public.
- Client-side guards are UX only. The backend is authoritative for every permission.
- Roles: `ADMIN`, `CASHIER`, `SERVER`; a user may hold several and permissions are the union of their roles. `RoleSet` is an internal partial record keyed by role, so permission checks are O(1); `src/services/api.ts` converts backend role arrays at the HTTP boundary and request bodies keep using arrays.
  - `ADMIN`: management area (users, catalog, settings, reports), counter sales, close/cancel table orders. Cannot open or edit tables.
  - `CASHIER`: counter sales, history, tables, close/cancel.
  - `SERVER`: tables and edits; cannot close orders.
  - Hide management navigation for non-admins and redirect direct visits.

## Icons

- Every icon usage is `<Icon name={IconName} size="sm" | "md" | "lg" color={...} />`.
- `Icon` lives in `src/components/icon/` and is the only adapter around `@expo/vector-icons`.
- `IconName` is an internal union of product-meaningful names such as `table`, `counter`, `payment`, `add`, `remove`, `settings`, `users`, `logout`, `back`, and `check`.
- The adapter owns a typed `Record<IconName, { set: IconSet; name: ExternalIconName }>` mapping. Size tokens: `sm = 16`, `md = 24`, `lg = 32`.
- Never import `@expo/vector-icons` outside `src/components/icon/`, and never pass raw vendor names through application code.

## Backend contract and API client

- Source of truth: the backend README and `GET /openapi.json` at <https://github.com/comando-systems/comando-backend>. When the backend changes, update the client types and this document in the same PR.
- `src/services/api.ts` is the single HTTP adapter. It reads `process.env.EXPO_PUBLIC_API_URL` (statically referenced as `process.env.EXPO_PUBLIC_API_URL`), sends `Content-Type: application/json`, attaches `Authorization: Bearer <accessToken>`, and normalizes errors to `{ code, message, details?, requestId? }`. Endpoint definitions call the typed `http.get`, `http.post`, `http.patch`, `http.put`, and `http.delete` helpers instead of constructing raw method options. The `errorMessages` map in that file is the single place where backend codes become fixed Portuguese messages; add a translation there whenever the backend introduces a code, including `ZERO_TOTAL` (409).
- IDs are decimal strings. All money values are integer cents. Timestamps are ISO 8601 UTC strings. Format for display only; never compute money with floats.
- On `401`, refresh once through `POST /auth/refresh`, store the rotated pair, and retry the original request. Refresh tokens are single use; a reused token revokes the whole family. On refresh failure, clear the session and return to `login`.
- Session persistence is an adapter in `src/services/storage.ts`: `expo-secure-store` on native, `localStorage` on web. Keep the token handling behind one interface; only that file checks `Platform.OS`.
- Types in `src/types/` mirror the backend serializers: `SessionResponse`, `UserResponse`, `ItemResponse`, `OrderResponse`, `OrderItemResponse`, `OrderPaymentResponse`, `SettingsResponse`, `SalesSummaryResponse`, and `PageResponse<T>`. Also mirror `RoleCode`, `OrderType`, `OrderStatus`, `PaymentMethod`, and request bodies.
- Primary endpoints used by the app:
  - `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout` (public).
  - `GET/POST/PATCH/DELETE /users`, `GET/PUT /settings`, `GET /reports/summary` (admin).
  - `GET/POST/PATCH/DELETE /items`; `GET /items` is the sellable catalog, `includeRemoved=true` is admin-only. The list query accepts `page`, `pageSize`, `includeRemoved`, and `search` (accent-insensitive over name, description, and primary category). The UI keeps search and category filtering local to the loaded page so that secondary categories are covered too.
  - `Item` carries `category` (primary) and `categories` (all labels, maximum 8, case-insensitively unique). `categories` replaces the whole set on write; the first entry becomes the primary `category`. There are no category CRUD endpoints: categories are managed only through items.
  - `POST /orders/counter` creates a **closed and paid** order in one call.
  - `POST /orders/table` opens an order with an optional `tableCode` (blank means unnamed); `POST /orders/:id/items`, `PATCH /orders/:id/items/:itemId`, `DELETE /orders/:id/items/:itemId` edit lines while `OPEN`.
  - `PATCH /orders/:id/pricing`, `POST /orders/:id/request-payment`, `POST /orders/:id/reopen`, `POST /orders/:id/close`, `POST /orders/:id/cancel`.
  - `GET /orders` accepts `status`, `statuses`, `type`, `tableCode`, `from`, `to`, `page`, and `pageSize`.
- Never trust client-calculated totals. The UI may preview pricing, but the backend result is authoritative after every mutation. A discount may exceed items plus surcharge, leaving a negative balance that closes without payments and charges no service fee; a zero total cannot be closed (`409 ZERO_TOTAL`), so the client blocks it before calling the backend. `OrderResponse` carries `originalTableCode`, which keeps the name after `tableCode` is cleared on finalization.

## Product behavior

### Order builder

- One reusable builder is used by tables and the counter: catalog browser, product image, name, unit price, quantity controls with decrease/increase buttons on both sides of the value, line total, subtotal, surcharge, discount, service fee, and total.
- Quantities are positive integers. Adding the same item again means increasing the existing line; there is one line per item per order.
- Surcharge and discount are independent integer-cent amounts; a discount above subtotal plus surcharge is allowed and previews a negative balance. No service fee is charged on a non-positive balance; the rate is a basis-point snapshot on the order.
- For a table order, mutations call the matching endpoint immediately and refresh the returned order.

### Tables

- The tables screen lists live table orders and lets an authorized user open a free table in one tap. The client picks the first free sequential name (`Mesa 1`, `Mesa 2`, …) from live table codes; the user can optionally rename it at open time. The backend accepts a blank `tableCode` (an unnamed table), but the generated name is still sent in the request. Opening a named table does not reserve it: a name becomes occupied only when an active order has lines, and line mutations then return `409 TABLE_OCCUPIED` with the existing order ID in `error.details.orderId`. Navigate to that order instead of showing an error.
- A table order can be saved for later payment with `request-payment` (`AWAITING_PAYMENT`) or reopened with `reopen`. Lines are locked while awaiting payment.
- The order screen offers **Save for later** (`request-payment`) and **Finish** (payment screen). Payment rows stay hidden until the user presses **Add payment**; amounts are entered in reais with two decimals and default to the amount due when a card/Pix method is selected. Only `CASH` may record `receivedCents`; the backend derives change and payments must sum exactly to a positive total. A zero total is blocked before closing with the `ZERO_TOTAL` message; a negative balance closes with no payments and hides **Add payment**.

### Counter

- The counter screen reuses the order builder. **Finish** reveals the payment area and **Confirm sale** creates the closed order.
- **Export to table** sits next to Finish and opens a select of live tables plus a **New table** option. It adds the built lines to the chosen order (or opens a generated `Mesa N` table) and discards the counter draft afterwards.
- Counter orders cannot be saved for later; the backend persists them as `CLOSED`.

### Management (admin only)

- Users: create, edit, reactivate, and deactivate. No public sign-up and no physical deletion. An admin cannot deactivate or demote themselves, and the last active admin cannot be removed.
- Catalog: create, edit, assign up to eight unique categories per item, enable/disable items and images, and remove items from the active catalog without destroying historical orders. Search and category filters are local to the loaded page and match any assigned category; pagination and `includeRemoved` come from the backend.
- Settings: service fee switch and rate in basis points (1000 = 10%). Only whole values from 0 to 10000 are accepted.
- Reports: sales summary for a date range, including revenue, ticket average, canceled and open orders, and totals by payment method. The range defaults to today in UTC and is entered with simple `YYYY-MM-DD` date fields (endpoint still receives ISO 8601 instants); all totals come from the backend.

## UI, state, and performance

- Build with React Native primitives (`View`, `Text`, `Pressable`, `ScrollView`, `FlatList`, `TextInput`, `Image`), never web-only DOM in shared code.
- Use safe-area-aware layouts, keyboard-friendly forms, loading and error states, and a consistent theme in one place. Styles are self-contained: never write inline `style={{ ... }}` objects in JSX; declare them in the file's `StyleSheet.create` and compose with arrays when a variation is needed. Extract a small component only when the same variation is genuinely reused.
- Visual direction follows the supplied design references: a full-width white header with the brand at left and highlighted navigation at right, white cards on a neutral gray background, and black primary text with orange money/active accents. Button variants are `primary` (orange fill), `secondary` (transparent with orange border/text), and `tertiary` (orange text only); no other variants are allowed. The logo source is `assets/full-logo.svg` (transparent background); `assets/full-logo.png` is generated from it with `rsvg-convert -w 480 -h 400 assets/full-logo.svg -o assets/full-logo.png` for React Native.
- On screens narrower than 700px, navigation becomes an icon-only bottom tab bar and the header shows only the logo; sign-out stays available as a header icon. Wide screens keep the header navigation and user details.
- Use the `theme.layout.formMaxWidth` token (320px) to cap `Field`, full-width `Button`, and `Form` on wide screens only; small screens use the full width. It must not constrain whole screens. Tables, Counter, and the order builder keep their full-width containers.
- List pages use the shared `Pagination` component with numbered page buttons instead of Previous/Next.
- Dedicated form screens use the `Form` component from `src/components/form/`. It centers the form, owns the submit and optional cancel actions, and limits its own width to the same token. The submit button is full width only when it is the only action; with cancel, both actions sit side by side. Pass loading, disabled, icon, and test ID through `submitButtonProps` / `cancelButtonProps`.
- Keep state close to its screen; use providers only for session and shared read-only data. Refresh order data after mutations rather than duplicating server calculations locally.
- Memoize expensive list rows and callbacks. Avoid storing volatile UI state in global stores.

## Testing and definition of done

- Jest uses the `jest-expo` preset. Tests live beside each component or screen implementation and use `@testing-library/react-native`.
- Git hooks in `.github/githooks/` enforce Conventional Commits and run lint, type checking, the full test suite, and tests scoped to staged source changes; `pnpm install` configures `core.hooksPath` on a fresh checkout and `pnpm run prepare` refreshes it.
- Cover success, invalid input, unauthorized access, and important edge cases for the unit under test. Mock external boundaries (API, storage, navigation), not the unit itself.
- Before declaring a change complete, run and pass:
  - `npx expo lint`
  - `npx tsc --noEmit`
  - `pnpm test`
  - `pnpm test:coverage` (enforces the 90% global threshold for statements, branches, functions, and lines)
  - `npx expo-doctor` when dependencies, app config, or SDK versions change
  - `npx expo export --platform web` when routing, bundling, or web behavior changes
- Update this file and the README whenever a decision, dependency, or contract changes.
- A change is complete only when the rules above are satisfied, no unrelated refactor or speculative abstraction was introduced, and all checks pass.
